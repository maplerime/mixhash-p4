# These python scripts read the AW c_api deliverables and produce
# C data structures that can be used to format debug output
# from register contents, generate higher level APIs, and 
# create the vector files.
#
# AW Firmware
# There are 3 (useful) FW files delivered from AW. Be careful to
# select the right 3 as they supply many different versions
# for simulation as well.
#
# - 16ln Eth (sw/mpro/linux/hexfile/silicon/eth_warriors_por.hex)
# - 4ln Eth (sw/mpro/linux/hexfile/silicon/eth.hex)
# - 4ln PCIe (sw/mpro/linux/hexfile/silicon/pcie.hex)
#
# The files come as .hex files. These are copied to
#   bf-drivers/src/alphawave/firmware/
#
# The primary inputs from a new c_api release are,
# - aw_alphacore_csr_defines.h
# - aw_alphacore_vfield_defines.h
# - aw_alphacore.c (the main API file)
# - FW files
#
# The above are duplicated in each IP version, 4ln and 16ln.
# Only the aw_alphacore_csr_defines.h file should differ
# between the two directories. The other files need to be 
# modified to match if any discrepancies are found, either
# by us or by AW.
#
# To integrate a new c_api release into the driver requires
# several manual steps. By far the most time consuming is
# constructing the aw_vector_types.h file from aw_alphacore.c.
#
# The aw_alphacore.c and .h files need a little modification.
# They come from AW as if they will be used stand-alone. So they
# define the same API names. To de-conflict these I have been
# modifying the prefix "aw_pmd_" with "aw_pmd_16ln_" or
# "aw_pmd_4ln_". It may be better to just declare them as
# "static", but that might require some changes to the build
# and I haven't explored it yet. So for now, just do a
# global replace of the API prefixes in each directory (and
# in both the aw_alphacore.c and .h files.
#
# They also define types used by the APIs. These types are 
# needed by bf_aw_pmd.c to call the APIs. So the types are moved
# one directory up and placed in aw_types.h
#
# Sometimes AW will have added a new typedef and use it, or a
# pointer to it, as an API parameter. This will cause bf-gen.py
# to output a bad line when calling the vector. This new type
# needs to be added to the list of type names stripped from
# the parameter list. You will find a long section of type
# names that get stripped in bf-gen.py. Just add it there. 
# Usually want to add not only the type but pointer-to-type
# as well, since there are _set and _get functions for most
# APIs.
#
# One quirk of the AW IP design involves the map_en bit. This bit
# is used to enable the external ANLT muxes in ANLT mode. We
# always have to have this bit set. However, when set, it changes
# where certain status and control bits show up. Some bits
# that are really in the RX slice will show up in the TX slice.
# This requires any access to those bits to reference the proper
# slice in the mss struct.
#
# To handle this, I have defined functions that will "correct"
# the mss struct for any reference to any of those bits. These
# functions are,
#
# bf_pmd_16ln_write_field
# bf_pmd_16ln_read_field
# bf_pmd_4ln_write_field
# bf_pmd_4ln_read_field
#
# All accesses to the DFX registers (DIG_SOC_LANE_*) must be
# modified to use these functions and not the standard ones,
#
# pmd_write_field
# pmd_read_field
#
#
# The Intel defined vectors and initialization code resides in
# bf_alphacore.c (in each directory). This file gets included
# by aw_alphacore.c
#
# Each API prototype can be grep'd out using,
#
# grep "int aw_pmd_" aw_alphacore.c > step1
#
# e.g.
# int aw_pmd_16ln_cmn_clkgen_refdiv_set(mss_access_t *mss, uint32_t div){
#
# Then "step1" can be edited to convert the prototypes to
# function pointer definitions.
#
# e.g.
# typedef int (*aw_pmd_cmn_clkgen_refdiv_set)(mss_access_t *mss, uint32_t div);
#
# These definitions are copied to the lower half of the file
# and edited to build the vector table itself.
#
# e.g.
# typedef struct aw_serdes_driver_vector_t {
#
# aw_pmd_cmn_clkgen_refdiv_set                    pmd_cmn_clkgen_refdiv_set;
#
#
# The vector table consists of a vector for each c_api as well
# as some Intel defined vectors. These can just be copied from
# release to release. They are identified by the comment
# "//bfn defined fns" in both the function pointer definition
# section at the top and the vector table portion at the bottom
# of the file.
#
#e.g.
# // bfn defined fns
# aw_pmd_mss_reset                               pmd_mss_reset;
# aw_pmd_fw_load                                 pmd_fw_load;
#
# You will also notice two other files being included in the 
# vector file,
#
# #include "vfld_vec_type.h"
# #include "vfld_vec_name.h"
#
# AW uses spare bits in scratch registers for what they call
# "virtual fields". These are usually knobs for the FW to use.
# We treat them as if they were normal CSR defines. However, they
# are generated by these scripts using the aw_alphacore_vfield_defines.h
# files as inputs.
#
# By including them in the vector table we can treat them as if
# they were APIs defined by AW.
